Agent fundamentals · Pure Python

从零手搓一个最小版 Agent

不碰 LangChain，也不碰 LangGraph。先用纯 Python 和假工具，把 Agent 最核心的执行闭环彻底看懂。

用户问题→ Planner→ Executor→ Verifier→ Retry / Next→ Final Answer

先看懂骨架，再接入大模型

很多 Agent 教程一开始就引入框架、模型 API、Tool Calling 和 JSON Schema。代码也许能跑，但很容易让人看不清 Agent 到底在做什么。

这里反过来：先使用假 LLM + 假工具，只关注 Planner、Executor、Verifier、State 与 Retry 是如何组成闭环的。骨架清楚后，再把固定逻辑替换成真正的大模型。

Agent 的核心并不神秘：一份持续更新的 State，加上一段会规划、执行、验证和重试的循环。

完整可运行代码

新建 mini_agent.py，复制下面的代码，然后运行 python mini_agent.py。

from typing import TypedDict, List


class AgentState(TypedDict):
    question: str
    plan: List[str]
    current_step: int
    results: List[str]
    retry_count: int
    final_answer: str


def weather_tool(city: str) -> str:
    """模拟天气查询工具。"""
    fake_weather_database = {
        "北京": "北京今天 12℃，小雨，有风",
        "上海": "上海今天 25℃，晴天",
        "广州": "广州今天 30℃，多云",
    }
    return fake_weather_database.get(city, f"没有找到 {city} 的天气")


def clothing_tool(weather: str) -> str:
    """用确定性规则生成穿衣建议。"""
    if "12℃" in weather:
        return "建议穿外套，最好带伞。"
    if "25℃" in weather:
        return "建议穿长袖或短袖。"
    if "30℃" in weather:
        return "天气比较热，建议穿短袖。"
    return "暂时无法给出穿衣建议。"


def planner(state: AgentState) -> AgentState:
    print("\n========== Planner ==========")
    print("用户问题：", state["question"])

    state["plan"] = [
        "查询北京天气",
        "根据天气给出穿衣建议",
    ]

    for index, step in enumerate(state["plan"]):
        print(f"Step {index + 1}: {step}")

    return state


def executor(state: AgentState) -> AgentState:
    print("\n========== Executor ==========")

    step = state["plan"][state["current_step"]]
    print("当前执行步骤：", step)

    if step == "查询北京天气":
        result = weather_tool("北京")
    elif step == "根据天气给出穿衣建议":
        weather = state["results"][0]
        result = clothing_tool(weather)
    else:
        result = "ERROR: 不知道应该调用什么工具"

    print("Tool 返回：", result)
    state["results"].append(result)
    return state


def verifier(state: AgentState) -> bool:
    print("\n========== Verifier ==========")

    latest_result = state["results"][-1]
    print("检查结果：", latest_result)

    success = "ERROR" not in latest_result
    print("执行成功 ✅" if success else "执行失败 ❌")
    return success


def generate_final_answer(state: AgentState) -> AgentState:
    print("\n========== Final Answer ==========")

    state["final_answer"] = "\n".join(state["results"])
    print(state["final_answer"])
    return state


def run_agent(question: str) -> AgentState:
    state: AgentState = {
        "question": question,
        "plan": [],
        "current_step": 0,
        "results": [],
        "retry_count": 0,
        "final_answer": "",
    }

    state = planner(state)

    while state["current_step"] < len(state["plan"]):
        state = executor(state)
        success = verifier(state)

        if success:
            state["current_step"] += 1
            state["retry_count"] = 0
            continue

        state["retry_count"] += 1
        print(f"当前步骤失败，第 {state['retry_count']} 次重试")

        if state["retry_count"] >= 3:
            print("连续失败 3 次，停止执行。")
            break

        state["results"].pop()

    if state["current_step"] == len(state["plan"]):
        state = generate_final_answer(state)

    return state


if __name__ == "__main__":
    run_agent("帮我查询北京今天的天气，并告诉我应该穿什么衣服")

把代码压缩成骨架

去掉日志、示例数据和注释，整套 Agent 的控制流其实只有下面这些：

state = init_state()
state = planner(state)

while not_finished(state):
    state = executor(state)
    success = verifier(state)

    if success:
        go_next_step(state)
    else:
        retry(state)

final_answer(state)

这段代码里最重要的不是某一个类，而是 while：执行结果会被检查，失败会回到循环，成功才进入下一步。

为什么一定要有 State？

State 可以理解为 Agent 手里的一张任务进度表。它保存用户问题、执行计划、当前步骤、历史结果、重试次数和最终答案。

第一步查询天气后，结果被写入 state["results"]；第二步再从同一份 State 里取出天气，生成穿衣建议。不同节点因此能够共享上下文。

{
    "question": "查询北京天气并给出穿衣建议",
    "plan": [
        "查询北京天气",
        "根据天气给出穿衣建议"
    ],
    "current_step": 1,
    "results": ["北京今天 12℃，小雨，有风"],
    "retry_count": 0,
    "final_answer": ""
}

State 就是 Agent 在整个 Workflow 中持续传递和更新的数据。

Node、Edge 与条件分支

Node：一个处理 State 的函数

planner(state)、executor(state) 和 verifier(state) 都可以看作节点。它们读取 State，完成一个明确职责，再返回结果。

Edge：决定下一步调用谁

当 Planner 结束后调用 Executor，这个调用关系就是一条 Edge。框架里的图结构，本质是在声明函数之间的流转顺序。

Conditional Edge：普通的 if / else

Verifier 判断成功时进入下一步，失败时回到 Executor 重试。所谓条件边，就是由运行结果决定接下来走哪条路径。

if success:
    next_step(state)
else:
    retry(state)

我的 Agent 心智模型

理解完代码骨架后，我会用一个更统一的模型来看 Agent：它既像一个拥有大脑、记忆和工具的人，也像一段被严格控制流约束的程序。

把 Agent 类比成人

Agent 里的组件类比人的能力
LLM大脑里负责理解、推理和生成的部分
State工作记忆 / 任务笔记本
Memory长期记忆
Tool手、眼睛、浏览器、计算器等外部能力
Planner先想“我要分几步做”
Verifier做完后检查“我做对了吗”
Router判断“这件事应该交给谁，或使用什么能力”
Agent Loop想 → 做 → 看结果 → 再想

State 不是完整的大脑，更像是“大脑允许自己显式记下来的工作区”。

如果系统只允许 State 保存下面这些字段，那么 Agent 后续就只能显式依赖这些信息继续运行：

state = {
    "goal": ...,
    "plan": ...,
    "current_step": ...,
    "tool_result": ...,
    "retry_count": ...
}

Agent 范式是人为设计的思维模板

Agent 看起来很灵活，但它的行为会被系统预先设计的“思考模式”限制。不同范式，本质是在规定 LLM 应该以什么顺序思考与行动。

ReAct

思考 → 调用工具 → 观察结果 → 再思考 → 再行动

Plan-and-Execute

先生成完整计划，再按照计划逐步执行

Reflection

先完成任务，再检查问题，根据反馈进行修改

因此，Agent 同时拥有两种看似矛盾的特征：LLM 的灵活性与程序控制流的确定性。系统可以要求它先规划、必须检查结果、失败只能重试，甚至连续失败三次后直接退出。

Tool 不思考，它只执行

Tool 本质上只是普通函数或外部 API。真正决定“要不要调用这个工具”的，是 Agent 或 LLM。

Agent 决定搜索 "GPT-6 price"
        ↓
程序调用 search()
        ↓
Tool 返回结果
        ↓
结果写回 State / messages
        ↓
LLM 读取 Observation，决定下一步

例如 calculator(a, b) 只负责返回计算结果。结果 42 会成为新的 Observation，Agent 再根据它决定是继续行动，还是生成最终答案。

统一模型：State → Reason → Act → Observe

State→ Reason→ Act→ Observe

Observation 会再次更新 State，然后进入下一轮 Reason。无论外层框架叫 ReAct、LangGraph 还是 Multi-Agent Orchestration，核心循环都可以压缩成这四步。

自由度与可控性的矛盾

完全放开 LLM，会获得更强的灵活性，也更容易出现跑偏、死循环、工具误用、Token 浪费和难以调试的问题。生产系统通常必须主动加上边界。

More freedom

探索空间更大，能处理更多未知场景，但行为更难预测与复现。

More control

系统更加安全、可观测和可验证，但需要工程师精心设计约束。

  • 最多执行 10 步，避免无限循环。
  • 只开放完成任务真正需要的工具。
  • 查询数据库前必须通过权限检查。
  • 生成 SQL 或重要结果后必须经过 Verifier。
  • 连续失败 3 次必须退出或重新规划。
  • 转账等高风险操作必须由人确认。

真正的 Agent 工程，不只是让 LLM 想得更自由，而是把这种自由限制在安全、可观测、可验证的轨道里。

所以这些看似零散的概念，其实都在回答同一个问题：当前知道什么 → 下一步谁来决定 → 做什么 → 得到什么 → 接下来去哪？

为什么暂时不用真正的 LLM？

如果一开始就加入模型调用，注意力很容易被消息格式、函数调用、结构化输出和异常解析分散。假工具让每一步都可预测，方便观察数据如何流动、失败如何重试。

学习顺序：先掌握确定性的 Agent Loop，再把 Planner、Executor 或 Verifier 中的固定逻辑逐步替换为模型调用。
